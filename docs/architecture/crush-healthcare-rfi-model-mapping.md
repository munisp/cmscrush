# CRUSH Healthcare Program-Integrity AI/ML Blueprint

**Author:** Manus AI  
**Status:** Architecture and model-selection blueprint; not legal advice, clinical advice, or a recommendation to automate enforcement.

## 1. Scope and interpretation

The authoritative problem statement is CMS’s Request for Information Related to Comprehensive Regulations To Uncover Suspicious Healthcare (CRUSH), Federal Register document 2026-03968. The RFI invites input on program-integrity requirements, provider identity and ownership, Medicare Advantage preclusion, laboratory/genetic/molecular testing, DMEPOS, Traditional Medicare claims, AI-assisted coding and hospital billing, beneficiary solicitation/contact, surety bonds, Medicaid/CHIP, state program-integrity operations, and FFE/SBE Marketplace integrity. [1]

The CRUSH platform is therefore a **healthcare program-integrity system**. Claims, encounter, enrollment, provider, beneficiary, clinical-document, laboratory, DMEPOS, ownership, referral, broker, and contact evidence are primary. TigerBeetle and Mojaloop are optional downstream integrations for authorized exposure accounting, reconciliation, or payment-network workflows; they are not the model-serving or clinical-integrity core.

The design uses the supplied nine-plane reference architecture and evidence-gated workflow. Data flows upward from ingestion through streaming, lakehouse, entity/knowledge graph, features, models, decision, and case/action. Governance flows downward through data-use controls, model cards, provenance, fairness, calibration, human review, and immutable audit. AI proposes and explains; authorized people and policy-controlled workflows decide.

## 2. Recommended open-source model portfolio

No single model should be called “the fraud model.” CRUSH should use a portfolio whose outputs are independently typed and fused by policy.

| Modality | Recommended open-source baseline | Role in CRUSH | License / qualification |
|---|---|---|---|
| Deterministic clinical NLP | MedSpaCy + spaCy ConText; Apache cTAKES | Sections, negation, uncertainty, temporal/context attributes, clinical concepts, codes, relations, and FHIR/CDA-oriented extraction. | MedSpaCy repository MIT; cTAKES Apache-2.0. cTAKES UMLS dictionary use requires a separate NLM UMLS license. [2] [3] |
| Biomedical concept linking | QuickUMLS/MedSpaCy, cTAKES dictionary lookup, terminology services | Candidate concepts mapped to SNOMED CT, RxNorm, ICD-10-CM, LOINC, CPT/HCPCS and local policy vocabularies. | Vocabulary and terminology rights must be checked separately; do not assume model-library license covers terminology content. |
| OCR/document layout | PaddleOCR PP-Structure; docTR; selectively PaddleOCR-VL | PDF/TIFF/fax ingestion, text boxes, tables, page layout, line/word coordinates, document classification, KIE. | PaddleOCR and docTR repositories Apache-2.0; verify individual model-weight terms before redistribution. [4] [5] |
| General constrained LLM | Qwen3-8B; Mistral-7B-Instruct-v0.3 | Retrieval-grounded evidence summaries, structured candidate extraction, discrepancy explanation, reviewer assistance, multilingual contact analysis. | Both referenced model cards list Apache-2.0. Mistral’s card notes no moderation mechanisms, so external policy and output gates are mandatory. [6] [7] |
| Speech/contact | OpenAI Whisper `small`/`medium`/`turbo` by measured language/SLO need | Local transcription, language identification, translation route, contact/sales-call evidence extraction. | Code and weights MIT; actual call-recording use still requires consent, retention, and privacy controls. [8] |
| Tabular supervised | LightGBM first; XGBoost/CatBoost challenger | Provider/claim/service-line risk, utilization residuals, high-dimensional categorical and temporal aggregates, calibrated prioritization. | LightGBM repository MIT; validate every dependency and model artifact. [9] |
| Tabular anomaly | PyOD detectors: Isolation Forest, ECOD/COPOD, HBOS, PCA/autoencoder only after baseline | Novel utilization, billing, timing, and contact anomalies where confirmed labels are sparse. | PyOD BSD-2-Clause and provides multi-modal detectors plus rejection/abstention APIs. [10] |
| GNN framework | PyTorch Geometric primary; DGL challenger | Heterogeneous/temporal provider–owner–beneficiary–claim–lab–DMEPOS–broker graph; node/edge risk and suspicious-subgraph prioritization. | PyG MIT; DGL Apache-2.0. [11] [12] |
| GNN architectures | Relation-aware message passing, GraphSAGE/GAT baseline, temporal graph model, graph autoencoder/anomaly challenger | Risk propagation over typed edges, temporal ring emergence, link anomaly, and investigator subgraph ranking. | Architecture code is CRUSH-owned; benchmark on point-in-time snapshots and do not treat explanations as proof. |
| Geospatial | Apache Sedona + Spark; bounded streaming spatial features; Postgres/PostGIS-compatible serving where approved | Provider distance, service-area anomalies, impossible travel, referral geography, density, cluster/community overlays, and state-border rules. | Use Sedona for reproducible spatial joins and geometry operations; retain source geometry/version and coordinate precision policy. |
| Explainability/calibration | SHAP for tree models; calibration curves/isotonic/Platt; conformal or interval output where validated | Reason codes, feature contributions, score bands, uncertainty, abstention, and reviewer evidence. | Explanations are evidence aids, not causal proof; retain the exact model and feature versions. |
| Drift/fairness | Evidently + NannyML; slice metrics and threshold governance | Data drift, concept drift, missingness, performance degradation, and protected/sensitive-group slice monitoring. | Use monitors as release gates and investigation triggers, not automated enforcement. |

### Portfolio choice

The production default should be **rules + LightGBM + PyOD + graph features**, with PyG GNNs in shadow mode. MedSpaCy/cTAKES and OCR/layout models should provide structured evidence before any LLM call. Qwen3-8B or Mistral-7B should be used as constrained, retrieval-grounded assistants; neither should be allowed to produce an unverified code, accusation, or adverse recommendation. The GNN should identify graph patterns and rank cases, while deterministic graph features remain the availability-safe baseline.

## 4. Dataset and data-contract plan

### Public and development-accessible sources

| Dataset/source | Use | Limitation |
|---|---|---|
| CMS Medicare SynPUFs | Schema, ETL, event replay, feature engineering, graph pipeline tests, dashboard demonstrations. | Synthetic; CMS states they have limited inferential value. Do not claim production fraud prevalence, generalization, or fairness from SynPUFs. [13] |
| CMS Medicare provider/utilization/payment public files | Provider/service/utilization baselines, aggregate outlier research, feature prototypes. | Public aggregates are not a complete fraud label source; reconcile vintage, suppression, and methodology. |
| NPPES/PECOS and provider enrollment public data | NPI taxonomy, enrollment/status, addresses, organizations, ownership/affiliation inputs where available. | Refresh cadence, field semantics, and legal-use limitations must be preserved as source metadata. |
| OIG LEIE and other approved exclusion/preclusion sources | Deterministic exclusion/preclusion features and list-diff events. | Effective dates and source authority must be honored; do not convert stale or ambiguous records into permanent adverse facts. |
| CMS Open Payments | Provider/industry-transfer-of-value contextual feature, network linkage, and transparency research. | Association is not evidence of fraud; retain source and reporting context. |
| Synthea | Fully synthetic patient/provider/encounter/FHIR data for integration and privacy-safe demos. | Synthetic distribution is not a production population and cannot validate operational fraud rates. |
| PhysioNet MIMIC-IV and similar controlled clinical datasets | Clinical-NLP, document/sequence, concept extraction, and de-identification development after authorized access. | Credentialed access/data-use agreement; not a CMS claims fraud label source. |
| Public standards and terminologies | FHIR, OMOP CDM, ICD-10-CM, HCPCS/CPT/LOINC/SNOMED/RxNorm mappings and coding-policy retrieval. | Each vocabulary/content license and version must be tracked independently from software licenses. |

### Production data classes

Production connectors should be separate for Traditional Medicare, MA/Part D, Medicaid/CHIP state programs, FFE/SBE, provider enrollment, exclusions, DMEPOS, laboratories, clinical records, and beneficiary contacts. Each connector emits a source-specific envelope with jurisdiction, effective time, ingestion time, source version, data-use basis, retention class, and content hash. Raw PHI/PII remains in encrypted tenant/state partitions. Shared telemetry receives only pseudonymous IDs, aggregate counters, feature/version references, and security metadata.

## 5. Evidence and label strategy

Confirmed fraud, waste, abuse, overpayment, underpayment, improper enrollment, and contact-abuse labels are outcome labels with delayed availability and selection bias. A referral, suspension, model score, or investigation opening is not a positive label. Store separate dispositions: `confirmed`, `not_substantiated`, `administrative_error`, `documentation_insufficient`, `provider_corrected`, `beneficiary_report_only`, and `unknown/pending`. Ray training jobs must use label availability times and point-in-time joins so future investigation outcomes cannot leak into pre-payment features.

A model’s success should be measured by workload-adjusted precision at review capacity, prevented improper-payment value where measurable, time-to-action, false-positive burden, calibration, abstention quality, subgroup parity, investigator acceptance/edit rate, and reproducibility—not only AUROC.

## 6. Deployment and legal-operational guardrails

The platform should be deployed as a recommendation and evidence system with human case workflows. It must not be marketed as an autonomous fraud adjudicator. The case plane owns notice, appeal, correction, statutory timers, and reviewer identity. The governance plane signs model cards, prompt policies, retrieval indexes, feature contracts, calibration artifacts, data snapshots, and release gates. Production models begin in shadow/challenger mode.

TigerBeetle, where used, records only separately authorized accounting facts. Mojaloop, where used, receives only a policy-authorized settlement command. Neither accepts model scores, LLM text, or GNN explanations as an authority field. These components are downstream controls and reconciliation mechanisms, not healthcare-fraud models.
